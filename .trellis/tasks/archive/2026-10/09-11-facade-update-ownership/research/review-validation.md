## Finding

### V1 — Low: full occupancy alone does not exercise drop-on-full

- **Artifact evidence:** `design.md:96` describes filling the capacity-100 outlet and then resuming its consumer. `design.md:107` and `prd.md:38` separately require a drop-on-full mutation to fail.
- **Source evidence:** `internal/infra/telegram/repo.go:82` allocates capacity 100; `internal/infra/telegram/repo.go:398` filters before the blocking publication at `internal/infra/telegram/repo.go:401`. The discriminating event must therefore be relevant and attempt publication while all 100 slots remain occupied.
- **Concrete counterexample, not an executed experiment:** feed exactly 100 relevant events, or resume the reader before publication of event 101. Both the intended blocking implementation and a faulty nonblocking/default-drop implementation can deliver the exact expected sequence. Filling the buffer has not exercised overflow.
- **Consequence:** a literal implementation of T4's described schedule can pass without distinguishing the prohibited repair. The mandatory mutation gate would then reject the test, but the schedule can be made precise now.
- **Smallest adequate correction:** require at least `cap(outlet)+1` distinct relevant events; keep the reader paused until the extra event has reached its publication attempt. Use a controlled input handoff plus quiescence/barriers, not merely producer enqueue completion or `len(outlet)==cap(outlet)`. Only then resume consumption and check the complete identities, contents, order, and count. Record the drop mutation failing specifically on missing delivery. No new production hook or queue policy is implied.
- **Blocks design approval:** **no**. The required red result already excludes this inadequate test, so this is implementation-test precision rather than an unresolved design decision. It **blocks implementation acceptance** if the mutation still passes or never reaches overflow.

## Fixture feasibility and failure cleanup

The supplemental evidence resolves the v1 feasibility question. `clientAdapter.GetListener` returns a concrete pointer (`internal/infra/telegram/client_adapter.go:51`), and the existing generated mock can return it (`internal/infra/telegram/mocks/client_adapter.go:695`). A non-nil-channel `&client.Listener{Updates: ch}` is source-constructible: `SDK/listener.go:47` has a zero-value mutex, and `SDK/listener.go:53` closes the channel without requiring private initialization. Unlike `SDK/client.go:130`, the literal does not activate or register a listener. It exercises the real Repo loop, not SDK fan-out. Compilation remains unverified here.

The v1.1 cleanup requirements are adequate design constraints, but T5's normal-receive cancellation is not sufficient evidence for the red cases. The following implementation checks make those constraints concrete:

1. Install cleanup before assertions or producer startup, within the controlled test lifetime. Synthetic producer sends need their own stop/cancellation path, including when the loop is bypassed or unexpectedly exits. Stop and join those producers before cancelling the Repo loop. A producer blocked on an unconditional input send cannot be joined this way. Keep the progress-assertion deadline separate from the loop's cancellation: an automatically expiring loop context could run its deferred Close while a producer is still active.
2. Record the progress/missing-event verdict **before** any rescue drainage. Rescue must not turn the observation into a green result. Register teardown so an assertion failure still executes it.
3. On the unconditional-allocation/publication control, inspect the **actual private outlet**, even though the case requested `NoBusinessUpdates`. If it is non-nil and publication is stalled, drain it during teardown so cancellation can be observed, then join the loop and the cleanup worker. Do not depend on the public `Updates()` accessor for cleanup: it intentionally panics for correctly disabled instances, and this mutation may have broken the mode/allocation invariant. Apply the same release discipline to enabled saturation cases.
4. Let `listenUpdates` be the sole input-channel closer. Do not close the fixture input or business outlet to force progress. `internal/infra/telegram/repo.go:371` defers listener closure; `SDK/listener.go:58` closes unconditionally, so a separate input close produces a double-close risk. `Repo.Close` only clears the adapter (`internal/infra/telegram/repo.go:102`); it is not a cancellation/join mechanism.

These checks follow from the bare publication at `internal/infra/telegram/repo.go:401`: its goroutine cannot observe the outer cancellation select while blocked there. They apply to failing disabled-mode controls as well as passing enabled-mode tests. The required old-behavior control restores both allocation and publication (`design.md:105`), so its channel is drainable. An intermediate nil-outlet/bare-send variant is different: neither draining another channel nor cancelling releases that send. Do not run such an additional control as an unjoinable shared-fixture goroutine; choose bounded isolated execution if it is intentionally included. No production cancellation redesign is required for the prescribed controls.

This is not an outstanding design blocker after `design.md:99` and `implement.md:20` explicitly require deterministic failure cleanup. The Linux implementation review must still verify the protocol on each behavioral-red path, not just T5 green.

Completion and readiness have source-specific preconditions:

- `clientDone` closes **before** `listenUpdates` starts (`internal/infra/telegram/repo.go:342`, `internal/infra/telegram/repo.go:344`). It cannot serve as a listener-ready or processing-complete barrier. A controlled `GetListener` handoff establishes fixture acquisition, not consumption of a particular event. Use an observed internal effect for the tail and a separate wrapper completion signal for joining the loop.
- Calling the loop directly also does not execute the authentication path that launches it at `internal/infra/telegram/repo.go:344`. Record the exact location of the bypass-listening mutation: a loop-level early return can be caught by this fixture; removing only the production launch cannot. The unchanged launch in both modes remains a source-review gate under `implement.md:28`, with actual facade startup exercised only by the separately authorized native probe. Do not describe the seam tests as startup coverage.
- `SendMessage` returns before `pendingSends.Store` (`internal/infra/telegram/repo.go:219`, `internal/infra/telegram/repo.go:227`). Injecting confirmation from the mock's return callback can precede registration and be lost legitimately at `internal/infra/telegram/repo.go:426`. Wait for the actual pending entry/result wait, then inject matching temporary IDs. Assert the permanent result or expected non-retryable error and pending-entry removal. The existing success/failure tests synchronize before directly dispatching (`internal/infra/telegram/repo_test.go:563`, `internal/infra/telegram/repo_test.go:725`); their synchronization can inform T3, but their helper injection cannot replace it.
- NewChat only signals an existing entry (`internal/infra/telegram/warmup.go:142`); `withReady` creates it before the initial operation (`internal/infra/telegram/warmup.go:250`). Establish the same-chat waiter and a stateful operation oracle before injection. Model materialization explicitly, feed NewChat through the listener, and require the waiting operation to complete before polling could rescue it. `withReady` rechecks the operation after the edge (`internal/infra/telegram/warmup.go:304`), so a closed entry alone is not readiness success.
- Existing `TestWithReady_ColdMissEdgeReleases` calls `table.signal` directly (`internal/infra/telegram/warmup_test.go:326`) and returns success by call ordinal (`internal/infra/telegram/warmup_test.go:315`). It is not evidence that the production NewChat branch remains wired. The new loop-driven test needs the event/state oracle required by `.trellis/spec/backend/quality-guidelines.md:46`. A missing NewChat branch must fail before ticker fallback, not merely produce a different count.

These are implementation gates under the existing ACs, not requests to redesign pending-send registration, readiness, or session lifetime. The observed registration timing is not a newly demonstrated production failure.

## Engine and LiveStack non-regression boundary

T4 is appropriately aimed at unchanged adapter delivery, not a proof of complete forwarding. Its real consumer must read the constructed Repo outlet; existing handler mocks alone cannot test that path. `handler.Run` reads it at `internal/app/handler/service.go:141` and dispatches send-success at `internal/app/handler/service.go:179`. LiveStack reads its own outlet at `internal/test/support/live_stack.go:189`, writes ID mappings at `internal/test/support/live_stack.go:201`, and consumes edits/deletes at `internal/test/support/live_stack.go:208` and `internal/test/support/live_stack.go:221`. This justifies T4's event selection, including confirmation delivery to both destinations.

Existing `TestRun_DispatchesMessageSendSucceeded` uses a mocked outlet and explicitly calls `ProcessAll` (`internal/app/handler/service_test.go:48`, `internal/app/handler/service_test.go:54`). It complements stream-level T4; it does not exercise engine assembly or the production scheduler. Correct role inspection in `design.md:44` and `design.md:53`, plus the final internal-suite regression run, is an adequate bounded gate without inventing a requirement for engine queue repair or live BDD execution. Do not turn preserved per-listener event order into a guarantee about asynchronous handler completion order or final delivery.

No new drop, retry, exactly-once, persistence, or engine-overload promise is needed to approve this design. An implementation that accidentally disables the engine/LiveStack outlet is rejected by the role gate even if all isolated Repo tests pass.

## CI, native acceptance, and limits

- The checked workflow runs `go vet ./...` and `go test ./internal/...` (`.github/workflows/ci-test.yml:121`, `.github/workflows/ci-test.yml:124`). Its scope comment explicitly excludes live-account BDD and does not include a race-detector gate (`.github/workflows/ci-test.yml:31`, `.github/workflows/ci-test.yml:36`). Compiling command/support packages does not execute their startup or LiveStack account flows.
- Linking native TDLib while running an inactive, unregistered listener fixture does not exercise real SDK receiver fan-out, request catchers, or sending/closing interleavings. `design.md:114` and `implement.md:58` preserve this distinction correctly. Absence of native E2E execution at the planning stage is not a design defect.
- Before production closure, the separately authorized probe in `design.md:116` must identify the actual asynchronous client-backed request, the known incoming-update load, the latency/error acceptance bounds, and the revision. For example, the existing history RPC reaches the adapter (`internal/transport/grpc/transport.go:89`, `internal/app/facade/service.go:109`, `internal/infra/telegram/client_adapter.go:251`) and pinned `SDK/function.go:2527` calls `client.Send`. This is a request-path example, not a proposal to reopen sparse-history investigation. A health response or package-level GetOption result is not interchangeable pump evidence (`internal/infra/telegram/client_adapter.go:342`). Cold readiness also needs an actual cold/waiting precondition, not a warm success mislabeled as edge coverage.
- If that environment is unavailable, native E2E and production-incident closure remain pending, as `implement.md:76` already states. Adapter-seam acceptance can be reported separately. No test-account access, request latency, exporter operation, mutation failure, or CI success was verified in this review.
- SDK lifecycle races, subscribed overload, authentication/session shutdown, and production engine scheduling remain the explicit exclusions in `prd.md:27` and `prd.md:28`. They are neither repaired nor silently made prerequisites for this local ownership change.
